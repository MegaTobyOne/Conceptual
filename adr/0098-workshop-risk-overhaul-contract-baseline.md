# 0098 — Workshop Risk overhaul: contract and interaction baseline

- Status: proposed
- Date: 2026-09-07
- Related: [docs/risk-overhaul-plan.md](../docs/risk-overhaul-plan.md) (programme plan and Phase 0 evidence), ADR 0003 (link taxonomy), ADR 0005 (default-deny publication), ADR 0008 (version axes), ADR 0012 (schema publication), ADR 0034 (Explorer local Risks), ADR 0067/0068 (6clicks risk source), ADR 0080 (strategy risk priority), ADR 0091 (schema-axis bump acceptance blocker), ADR 0096 (Essentials surface budget), ADR 0097 (owner is a team label, never a person).

This ADR is the Phase 0 output of the Workshop Risk overhaul. It records the decisions the programme needs before any contract change, marks which of them are **proposed** (recommended by Phase 0, awaiting operator approval) and which are **blocking** (Phase 1A cannot start until the operator chooses), and fixes the field, link and publication tables that Phase 1A will implement. Nothing in this ADR is implemented. Accepting this ADR does not allocate a release, a schema version or permission to publish.

## Context

### What exists today (verified 2026-09-07 at product `1.74.0`, axes `1.16.0`)

`RiskEntity` in `packages/contracts/src/index.ts` is a fixed-score record: `title`, `status` (`open | monitored | closed`), `likelihood: number`, `impact: number` and optional 6clicks `integration` metadata. Every field except `integration` is **public**; the sanitiser projects `integration` to `{ sourceLabel, remoteUpdatedAt }`. The published schema `schemas/explorer-bundle/1.16.0/collections/risks.schema.json` **requires** `likelihood` and `impact` as integers 1–5, so a Risk with no score cannot be published under the current schema at all.

Validation is Workshop-form-only. Core `validateEntityWriteRules` has no Risk rule, `importBundle` never calls `prepareEntitiesForWrite`, and the sanitiser throws on any field without a declared policy. That last property is the one safety net: a new Risk field with no policy fails export closed rather than leaking.

Score consumers disagree with each other and with invariant E5 (`<5` Low, `5..9` Medium, `10..15` High, `>=16` Extreme):

| Consumer                                                                      | Rule                                                      | Divergence from E5                                                      |
| ----------------------------------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------- |
| Explorer `riskBandOf` (`packages/explorer/src/domain/analytics.ts`)           | E5                                                        | none                                                                    |
| Workshop tree label `workshopRiskSeverityLabel` (`extension.ts`)              | `>=16` Extreme, `>=10` High, `>=4` Medium                 | score 4 is labelled Medium; E5 says Low                                 |
| Workshop `CONTINUOUS_COMPLIANCE_RISK_SEVERITIES` (`continuous-compliance.ts`) | three bands: High `>=15`, Medium `>=8`, Low `>=1`         | different band count and boundaries; feeds strategy priority (ADR 0080) |
| Core snapshot `highOrExtremeRiskTotal` (`service.ts`)                         | `likelihood × impact >= 10`                               | consistent with E5 High+Extreme                                         |
| Shop supplier attention (`packages/shop/src/extension.ts`)                    | `open` or score `>= 12`                                   | ad hoc threshold                                                        |
| Contracts consequence chain / suggested actions                               | `(likelihood ?? 0) * (impact ?? 0)`, `>=10`/`>=5` weights | a missing score silently becomes 0 = "Low"                              |
| Connected View                                                                | clamps each factor to 1..5 then multiplies                | hides out-of-range data                                                 |

`treated-by` is in `LINK_TYPES` and Connected View reads `risk -> treated-by -> action`, but there is **no** `OPERATOR_LINK_RULES` entry and **no** Workshop authoring path for it. Workshop can only author `requirement -> exposed-by -> risk` and `source-control -> exposed-by -> risk`; Shop authors `supplier -> associated-with -> risk`.

`pspf-entity-link-spec.md` § Risk documents a different shape (string bands, `riskType`, `residualLevel`, `treatmentStatus`, `ownerPersonId`, `acceptedBy`, status `open | accepted | treated | closed`) that has never been implemented and that contradicts ADR 0097 D5 (no person ownership fields). This ADR supersedes that section; the spec must be corrected in Phase 1A rather than left as a second source of truth.

The Workshop `exportBackupJson` command delegates to `pspf.core.exportBundle`, which is publication-sanitised. It is not a lossless backup and must not be described as one for any new sensitive Risk field.

### Constraints carried forward

- Workshop only; the Explorer interface, routes and nav are unchanged. Incompatible publication fails at preflight; nothing invents legacy scores or drops records.
- Essentials surface budget (`scripts/lib/essentials-surface-baseline.json`: Workshop 72 commands, 30 webview panels) is not increased.
- Default-deny publication; every new field, nested or not, declares `publication`.
- Three compatibility axes only. A methodology revision ID is provenance inside data, never a fourth axis.
- Local-first; no network, authentication or 6clicks behaviour change.

## Decisions

Each decision row states the Phase 0 recommendation and its approval state. **Proposed** rows are recommended and can be accepted by the operator without further design. **Blocking** rows need an operator choice before Phase 1A begins. Rows marked **Deferred** are explicitly out of Phase 1A/1B and will be revisited by the named later phase.

### D1 — Assessment shape and meaning of legacy scores

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                         | State    |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 1.1 | Risk carries `assessment?: RiskAssessment`, a discriminated union: `{ basis: "unassessed" }`, `{ basis: "legacy", likelihood: 1..5, impact: 1..5, assessedAt?, rationale? }`, or `{ basis: "custom", methodologyId, revisionId, current, inherent?, target?, assessedAt, rationale? }`.                                                                                                                                          | Proposed |
| 1.2 | Existing `likelihood`/`impact` remain on the entity **unchanged** during Phase 1A/1B and continue to be the published legacy projection. A Risk with `likelihood`/`impact` and no `assessment` is read as `{ basis: "legacy" }` by the shared evaluator. No record is rewritten by migration.                                                                                                                                    | Proposed |
| 1.3 | A shared evaluator `evaluateRisk(risk, framework)` in `@pspf/contracts` returns `{ state: "assessed" \| "unassessed" \| "legacy" \| "not-comparable", band?, score?, methodologyRef, explanation }`. Every consumer listed in Context calls it; none multiplies `likelihood × impact` directly.                                                                                                                                  | Proposed |
| 1.4 | Missing scores never coerce to `0`, `Low` or the lowest band. Consumers that need a single number (strategy priority, suggested-action impact, Shop attention) must either exclude the record and disclose the excluded count, or treat `unassessed`/`not-comparable` as a distinct branch.                                                                                                                                      | Proposed |
| 1.5 | Legacy numbers mean the invariant E5 four-band 5×5 methodology. The Workshop tree label (`>=4` Medium) and the three-band `CONTINUOUS_COMPLIANCE_RISK_SEVERITIES` are **defects** relative to E5 and are corrected to E5 in Phase 1C. ADR 0080 strategy priority weights are re-expressed on E5 bands with a fixture proving unchanged ordering for existing sample data, or the ordering change is disclosed in the 1C handoff. | Proposed |
| 1.6 | Whether a `custom` assessment may be published to Explorer under a schema that only knows legacy 1–5 scores. Recommendation: **no** in this programme; publication of any `custom`-basis Risk is blocked at preflight (D6). The alternative — a schema bump that makes `likelihood`/`impact` optional and adds a public `assessmentState` — is a later ADR.                                                                      | Blocking |

### D2 — Framework, categories, methodology and appetite

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                    | State    |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 2.1 | One Core-owned singleton entity `risk-framework` (ID prefix `RFW`, collection `risk-frameworks`, max one non-deleted record per workspace) holds `categories[]`, `methodologies[]`, `appetiteRules[]`, `sourceRegisters[]` and `presentationPresets[]`. It is workspace data, not VS Code settings.                                                                                                         | Proposed |
| 2.2 | Categories are `{ id, label, parentId?, order, archived }` nodes inside the framework. IDs are stable ULID-style strings prefixed `cat_`, unique within the framework. Rename/reorder/archive are allowed; delete is rejected while any Risk references the node. Categories are **not** entities, not Domains, and carry no appetite of their own beyond an appetite rule that names them.                 | Proposed |
| 2.3 | A Risk has at most one `primaryCategoryId`. Reclassification is an ordinary field edit that emits a `risk-event` of kind `reclassified` (D4) and shows an appetite-change preview when the effective rule changes.                                                                                                                                                                                          | Proposed |
| 2.4 | Methodology: `{ id, label, revisions: [{ revisionId, activatedAt, likelihoodLevels: [{ id, label, order }], impactLevels: [...], cells: [{ likelihoodId, impactId, bandId, score? }], bands: [{ id, label, order, colourToken }] }] }`. Bounds: 2–10 levels per axis, every cell must map to a band, no formulas. Revisions are immutable once `activatedAt` is set; a new revision is a new array element. | Proposed |
| 2.5 | The seeded methodology `legacy-5x5` revision `r1` encodes E5 exactly. It is created by Phase 1B migration only when the operator opens the framework editor or runs the explicit migration command; a workspace with no framework record behaves as today.                                                                                                                                                  | Proposed |
| 2.6 | Appetite rule: `{ id, scope: { kind: "workspace" } \| { kind: "category", categoryId }, methodologyId, revisionId, allowedBandIds[], rationale, effectiveFrom, reviewBy? }`. Resolution: nearest explicit category rule walking `parentId` upward, else workspace rule, else "Appetite not set".                                                                                                            | Proposed |
| 2.7 | Expired-rule behaviour (`reviewBy` in the past). Recommendation: the rule **still applies** and the evaluator returns `appetite: { state: "in-appetite" \| "over-appetite", stale: true }`; the workbench shows "Appetite review overdue". Alternative: treat as "Appetite not set".                                                                                                                        | Blocking |
| 2.8 | Every nested framework field is `sensitive` except structural identifiers needed for Core round-trip (`id`, `entityType`, `schemaVersion`, envelope fields). The framework collection is present in the master bundle so Core round-trips it, but the sanitiser strips all labels, rationale and cells. Explorer receives an empty shell and ignores it.                                                    | Proposed |

### D3 — Hierarchy, secondary associations and control applications

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | State    |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 3.1 | Primary parent is the link `child risk -> rolls-up-to -> parent risk`. `rolls-up-to` is a **new** `LinkType`. Cardinality: at most one non-deleted outgoing `rolls-up-to` per Risk. No `parentRiskId` field exists on the entity; the link is the single source of truth.                                                                                                                                                                                                                                                                                                                                                                                                           | Proposed |
| 3.2 | Secondary enterprise association is `risk -> related-to -> risk` using the existing `related-to` type with a new optional `LinkEntity.linkRole` field set to `"secondary-enterprise-association"`. `LinkEntity` today carries only `evidenceNote`/`evidenceSection` as optional metadata, so `linkRole` is a contract addition with its own (`public`, enum-only) publication policy. Unbounded cardinality. It never affects appetite inheritance or roll-up counts.                                                                                                                                                                                                               | Proposed |
| 3.3 | Cycle detection runs in Core `prepareEntitiesForWrite` and in `buildImportPlan` over the proposed final graph (`stored ∪ incoming − deleted`). Self-links, cycles and dangling endpoints are rejected with a `PspfError` naming the path.                                                                                                                                                                                                                                                                                                                                                                                                                                           | Proposed |
| 3.4 | Organisational control is a new entity `risk-control` (ID prefix `RCT`, collection `risk-controls`) with `title`, `definition` (sensitive), `ownerTeam` (sensitive), `state: "proposed" \| "active" \| "retired"`, `reviewBy?`, optional `sourceControlIds[]` referencing vendored ISM controls read-only.                                                                                                                                                                                                                                                                                                                                                                          | Proposed |
| 3.5 | Control application representation. Recommendation: **typed link metadata** — a new optional `LinkEntity.application` object (`sensitive`) permitted only when `linkType === "mitigated-by"`, carrying `{ role: "preventive" \| "recovery" \| "both", applicability, effectiveness: "not-assessed" \| "ineffective" \| "partially-effective" \| "effective", rationale?, anchorIds[] }`. Alternative: a dedicated `risk-control-application` entity. Typed metadata keeps one relationship record and extends the existing optional-metadata precedent (`evidenceNote`); a dedicated entity would be needed only if applications need their own history, which D4 does not require. | Blocking |
| 3.6 | Causes and consequences are `{ id, label }` arrays on the Risk (`causes[]`, `consequences[]`), IDs prefixed `cause_`/`cons_`, unique within the Risk. `anchorIds` on a control application must resolve to the owning Risk's cause/consequence IDs or the write is rejected.                                                                                                                                                                                                                                                                                                                                                                                                        | Proposed |
| 3.7 | Treatments reuse canonical Actions via `risk -> treated-by -> action`. Phase 1A adds the missing `OPERATOR_LINK_RULES` entry (`workshop-risk-treated-by-action`, label "Link Action to Risk", phrase "treated by"). No treatment register, no treatment-specific fields on Action.                                                                                                                                                                                                                                                                                                                                                                                                  | Proposed |
| 3.8 | Roll-up summaries count **distinct** treatment/control IDs, distinguish direct from descendant coverage, and never sum or average ordinal bands.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Proposed |

### D4 — Events, escalation and correction

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                     | State    |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 4.1 | New Core-owned entity `risk-event` (ID prefix `RSE`, collection `risk-events`): `{ riskId, kind: "reassessed" \| "reparented" \| "reclassified" \| "reconciled" \| "escalation", occurredAt, summary (sensitive), before?, after?, escalation?: { state: "proposed" \| "accepted" \| "declined" \| "withdrawn", destinationRiskId?, governanceLabel?, reason (sensitive), decidedAt?, references[] } }`.                     | Proposed |
| 4.2 | Core is the only author. `prepareEntitiesForWrite` derives events from the diff between stored and incoming Risk (assessment change, `rolls-up-to` change, `primaryCategoryId` change) and appends them in the same SQL transaction, exactly as `appendDueDateHistory` does for Actions. Client-supplied `risk-event` entities are rejected on write and on import unless they match an existing stored event byte-for-byte. | Proposed |
| 4.3 | No-op saves (deep-equal Risk) emit no event. Corrections append a new event; events are never edited or deleted except through the existing redaction-event mechanism (ADR 0006).                                                                                                                                                                                                                                            | Proposed |
| 4.4 | Escalation is operator-authored through a Workshop action that produces an `escalation` event; it never changes category, parent, status or assessment. Accepted escalation may offer a separately previewed reparent/reclassify edit which, if confirmed, produces its own events.                                                                                                                                          | Proposed |
| 4.5 | Change Records with `changeType: "risk-response"` and `change-record -> changes -> risk` remain the narrative decision stream. They are not generated from events and events are not generated from them.                                                                                                                                                                                                                    | Proposed |
| 4.6 | Undo/restore for Risk writes uses the existing import undo point and full-replace rollback mechanisms; no new undo surface. Restoring a pre-import state restores its `risk-events` collection with it, so history and facts stay consistent.                                                                                                                                                                                | Proposed |

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                      | State    |

The only new **public** fields are `assessmentState` (the evaluator's four-value state) and `primaryCategoryId` (an opaque ID). ## Field, link and policy tables for Phase 1A

New Risk fields (all optional unless stated; publication per ADR 0005 default-deny):

| Field                  | Type                                                          | Publication | Note                                                  |
| ---------------------- | ------------------------------------------------------------- | ----------- | ----------------------------------------------------- |
| `reference`            | string                                                        | sensitive   | operator's own register reference, distinct from `id` |
| `description`          | string                                                        | sensitive   | free text                                             |
| `causes`               | `{ id, label }[]`                                             | sensitive   | stable IDs, bow-tie anchors                           |
| `consequences`         | `{ id, label }[]`                                             | sensitive   | stable IDs, bow-tie anchors                           |
| `primaryCategoryId`    | string                                                        | public      | opaque framework node ID; label is never published    |
| `ownerTeam`            | string                                                        | sensitive   | team label, ADR 0097 D5                               |
| `reviewBy`             | ISO date-time                                                 | sensitive   |                                                       |
| `assessment`           | `RiskAssessment` union (D1.1)                                 | sensitive   | includes rationale and methodology refs               |
| `assessmentState`      | `"assessed" \| "unassessed" \| "legacy" \| "not-comparable"`  | public      | derived by Core on write from `assessment`; read-only |
| `response`             | `"reduce" \| "avoid" \| "share" \| "accept" \| "not-decided"` | sensitive   |                                                       |
| `externalRefs`         | D5.4 shape `[]`                                               | sensitive   | `referenceUrl` validated `https:` without userinfo    |
| `likelihood`, `impact` | unchanged, required                                           | public      | legacy projection; unchanged in this programme        |
| `integration`          | unchanged                                                     | sensitive   | existing 6clicks projection unchanged                 |

New entities: `risk-framework` (`RFW`, singleton), `risk-control` (`RCT`), `risk-event` (`RSE`). All non-envelope fields `sensitive`.

New link rules (`OPERATOR_LINK_RULES`):

| From   | Link         | To           | Cardinality           | Validation                                              |
| ------ | ------------ | ------------ | --------------------- | ------------------------------------------------------- |
| risk   | rolls-up-to  | risk         | ≤ 1 outgoing per risk | no self-link, no cycle, endpoints exist and not deleted |
| risk   | related-to   | risk         | many                  | `linkRole` required; no self-link                       |
| risk   | treated-by   | action       | many                  | endpoints exist; existing taxonomy, new operator rule   |
| risk   | mitigated-by | risk-control | many                  | typed metadata (D3.5); anchors resolve on the risk      |
| action | addressed-by | risk-control | many                  | existing type; "action closes a control gap"            |

Consumers to adapt in Phase 1C (must call `evaluateRisk`): Workshop tree label and `CONTINUOUS_COMPLIANCE_RISK_SEVERITIES`; Core `highOrExtremeRiskTotal`; Shop supplier attention; contracts consequence chain and suggested actions; Connected View score; Explorer `riskBandOf` is left as-is because it only ever receives legacy-projected records.

## Compatibility and recovery strategy

1. Phase 1A changes contracts and tests only; nothing is persisted differently until Phase 1B.
2. Phase 1B lands the schema bump, Core validation, event derivation, preflight and the cold-restore proof in one release. Before that release, the runbook's backup path is executed against a fixture workspace and the evidence recorded in the plan.
3. Until a later Explorer-aware ADR, any workspace using `custom` assessments, `rolls-up-to` or `mitigated-by` cannot export or team-share; preflight says so with the offending IDs. Legacy-only workspaces are unaffected apart from the axis bump, which preflight explains to older Explorer readers.
4. Publication JSON is never described as backup. UI copy for the two Workshop bundle commands changes accordingly (D7.2).

## Consequences

Positive:

- Every derived consumer stops fabricating a band from missing or incomparable data; the three existing band defects are fixed against E5 rather than left to drift.
- One relationship record per fact (link for parent, link metadata for control application, Core-derived events for history) gives Core one validation path for writes and imports.
- Explorer needs no change in this programme, and the public projection of a legacy Risk is byte-identical, so the axis bump is the only compatibility event.
- The operator sees the export consequence of adopting a custom methodology before adopting it.

Negative / accepted costs:

- Workspaces on custom methodologies lose master export and team-share until a later ADR (if D1.6/D6.5 resolve as recommended).
- One more Core-owned singleton and two more collections increase schema surface; batching into one bump limits the review cost.
- Removing the aspirational Risk section from `pspf-entity-link-spec.md` is a visible correction of previously published documentation.

## Operator approvals required before Phase 1A

- D1.6 / D6.5 — block publication of custom-basis Risks in this programme (recommended), or fund a schema change that makes `likelihood`/`impact` optional now.
- D2.7 — expired appetite rule still applies and is flagged stale (recommended), or is treated as "Appetite not set".
- D3.5 — typed link metadata for control applications (recommended), or a dedicated `risk-control-application` entity.

All other rows are proposed and become accepted when this ADR's status changes to `accepted`. Until then, the status stays `proposed` and no Phase 1A code is written.
